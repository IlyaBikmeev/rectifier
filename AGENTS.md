# Rectifier

Домашний сервис мониторинга и автоматизации ректификационной колонны на Raspberry Pi 5.

## Стек

- Go
- Raspberry Pi 5
- DS18B20 через Linux 1-Wire
- `net/http` для локального Web UI/API
- Vanilla JavaScript с ES modules без frontend build step
- Bootstrap и Chart.js для UI
- Prometheus-совместимый `/metrics`
- Grafana Alloy → Grafana Cloud
- SQLite для партий, запусков, датчиков и измерений

## Архитектурные принципы

- `cmd/rectifier` — точка входа приложения.
- Основной код находится в `internal`.
- `internal/app/templates/index.html` содержит основную HTML-разметку, а
  пользовательские CSS и JavaScript находятся в `internal/app/static`.
- `internal/app/static/js/app.js` — единственная frontend-точка входа и место
  высокоуровневого связывания модулей.
- Не добавлять фреймворки и внешние зависимости без необходимости.
- Предпочитать стандартную библиотеку Go.
- Hardware-логику отделять от логики приложения.
- UI, metrics и будущие hardware outputs должны работать поверх общего состояния приложения.
- Приложение должно корректно работать как долгоживущий systemd-сервис на Raspberry Pi.
- Учитывать graceful shutdown через `context.Context`.

## Текущий этап

Проект находится на раннем этапе разработки.

Сейчас реализован минимальный сервис:

1. HTTP-сервер.
2. Локальный Web UI.
3. Чтение DS18B20.
4. Запуск Run и сохранение измерений.
5. Prometheus `/metrics`.
6. Полный жизненный цикл Start/Stop с сохранением измерений.
7. График активного Run и восстановление активного Run после перезапуска.
8. Frontend разделён на ES modules по ответственности: API, routing, sensors,
   Runs и Chart.js.
9. История партий и Runs с пагинацией, графиками и live-обновлением.
10. Ручные метки на графиках активных и завершённых Runs.

Ближайший этап — runtime-rescan датчиков.

Пока не реализуем OLED, управление нагревом и другую аппаратную автоматику.

## Подход к разработке

- Реализовывать функции небольшими сквозными срезами: SQLite → repository →
  `AppState` → HTTP API → UI.
- SQLite является источником истины для долговременного состояния, а `AppState`
  — потокобезопасным оперативным снимком.
- Сначала успешно сохранять изменение в SQLite и только затем менять `AppState`.
- UI может немедленно показать результат успешной команды, но обязан подтвердить
  его повторной синхронизацией через `/api/process`.
- При потере синхронизации блокировать действия, изменяющие состояние.
- Не имитировать Start/Stop только на клиенте.
- Использовать существующие Bootstrap, Chart.js и vanilla ES modules. Не
  добавлять frontend-фреймворк, package manager или build step без необходимости.
- Для оформления UI использовать только классы и компоненты Bootstrap и
  Bootstrap Icons. Не добавлять и не изменять пользовательские CSS-стили.
- Сохранять границы frontend-модулей: `api.js` не содержит DOM-логики,
  `router.js` отвечает за hash navigation, `sensors.js` — за датчики,
  `runs.js` — за жизненный цикл Run, `history.js` — за историю,
  `run-events.js` — за создание меток, `chart.js` — за график и отображение
  меток, а `app.js` только связывает модули.
- Сохранять hardware-логику отдельно от жизненного цикла Run.
- Для каждого среза проверять API, состояние SQLite, затронутые frontend-модули,
  UI, `git diff --check` и `go test ./...`.
- При изменении архитектуры, поведения, API, структуры каталогов, процесса
  запуска или разработки обновлять связанные `README.md`, документы в `docs`
  и инструкции `AGENTS.md` в том же срезе. Не оставлять заведомо устаревшие
  описания и команды.

## Стиль разработки

Проект также используется для изучения Go.

Не переусложнять решения и не генерировать большие объёмы кода без необходимости.
Предпочитать небольшие, понятные изменения.
При возможности объяснять используемые Go-механизмы, а не скрывать их за абстракциями.
